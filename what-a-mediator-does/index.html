why mediators exist

Most agents can't be reached directly.

Phones sleep, change networks and sit behind NAT. Agents inside a firewall have no public address. A DIDComm endpoint has to be something a sender can deliver to while the recipient is away.

The routing protocol defines how a sender and a recipient cooperate, using a partly trusted mediator, to facilitate message delivery. No party is required to know the full route of a message.DIDComm Messaging v2.1 — Routing Protocol 2.0

the only message

Routing 2.0 has exactly one message type: forward

{
  "type": "https://didcomm.org/routing/2.0/forward",
  "id": "abc123xyz456",
  "to": ["did:example:mediator"],
  "expires_time": 1516385931,
  "body": {
    "next": "did:foo:1234abcd"
  },
  "attachments": [
    // encrypted for the next hop
  ]
}
  • next: who to hand the attachment to. Usually a DID; can be a key for the last hop.
  • attachments: the payload, already encrypted for next. The mediator can't open it.
  • Optional: expires_time, and delay_milli to ask for delayed (or, if negative, randomly delayed) delivery.

wrapping

How a sender builds the onion

Plaintext

Build the message. Sign it first if non-repudiation is needed.

Encrypt for the recipient

One envelope per recipient DID, decryptable by any of its keyAgreement keys.

Wrap, back to front

For each entry in routingKeys, last one first: put the current message in a forward and encrypt it for that key.

Send

Deliver the outermost layer to the uri in the recipient's service endpoint.

Each hop peels one layer, learns only the next hop, and passes the rest on.

What a mediator can and can't see

Can see

The next hop (next), message sizes, timing, and volume. Enough to learn who receives a lot of traffic, and when.

Can't see

The content, the message type, or (with the right envelope) who the sender is.

Authcrypt puts the sender's key id (skid) in the envelope header. The spec's anoncrypt(authcrypt(plaintext)) combination hides it from the hop just before the mediator.

an optional trick

Rewrapping keeps the onion the same size

Instead of passing the inner payload on as-is, a mediator can put it in a fresh forward addressed to the recipient itself.

  • Messages don't visibly shrink hop by hop.
  • The mediator can add or remove padding, and its own tracing.
  • Routing can change late in the delivery chain.
These last two characteristics could provide the foundation of mixnet features for DIDComm; however, such functionality is out of scope in this spec.Routing Protocol 2.0 — Rewrapping

indirection that helps

A mediator's DID as your endpoint

{
  "id": "did:example:123#didcomm-1",
  "type": "DIDCommMessaging",
  "serviceEndpoint": {
    "uri": "did:example:somemediator"
  }
}
  • The sender resolves the mediator's DID, prepends its keyAgreement keys to the routing keys, and delivers to its endpoints.
  • The mediator can rotate keys or move servers without every one of its users updating their DID documents.
  • A mediator's own DID document should use plain transport URIs, to avoid recursive resolution.

many envelope formats

One endpoint can speak several profiles

A service endpoint's accept list names profiles, in order of preference. Each profile fixes the envelope, signing, plaintext and routing conventions together.

ProfileMeaning
didcomm/v2Everything as defined by DIDComm Messaging v2.x
didcomm/aip2;env=rfc587Aries AIP 2.0 with the newer encryption envelope (RFC 0587)
didcomm/aip2;env=rfc19Aries AIP 2.0 with the older envelope (RFC 0019)
didcomm/aip1Aries AIP 1.0, i.e. DIDComm v1-era conventions

There is deliberately no negotiation mechanism: the spec says it "would create a recursive versioning problem of its own".

no public endpoint at all

Replies over the same connection

DIDComm transports are one-way. The return-route extension lets an agent with no public endpoint ask for messages to come back over the connection it opened.

none

Default. Nothing comes back this way.

all

Send me everything for this DID over this connection.

thread

Only messages in the named thread.

Only between directly connected agents; it isn't valid when routing keys are in use.

reliability

More than one way in

  • A DID document can list several service endpoints, in the owner's order of preference; "Any endpoint MAY be selected by the sender."
  • Failover is expected: "If the transmission of a message fails, the sender SHOULD try another endpoint or try delivery at a later time."
  • A message goes to one endpoint, not all of them, so two mediators don't both deliver it.
  • please_ack is for the ultimate sender and receiver only; mediators MUST NOT honor it.
