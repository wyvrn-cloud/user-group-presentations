draft
the problem with inline

Big messages hurt everyone on the route

An attachment can ride inside the message as base64. Fine for a thumbnail. For a video it means every mediator queues, stores and forwards the whole thing, base64'd, possibly once per recipient.

Size limits

Receivers can declare max_receive_bytes and discard anything larger.

Mediator load

A relay built to forward small messages now holds large blobs until pickup.

All or nothing

No resuming: a dropped transfer starts again from the first byte.

the spec already allows references

Attachments by value or by reference

  • base64 / json: content inline.
  • links: where to fetch it. When used, a hash is required so the receiver can check what it downloaded.
  • byte_count: how big, so the receiver can decide when (or whether) to fetch.
  • jws: a detached signature over the content, from anyone.
The attachment(s) in the attachments field are able to use the full power of DIDComm attachments, including features like instructing the receiver to download the payload content from a CDN.Routing Protocol 2.0 — Messages

the registry's pattern

Encrypt, upload, share the key: media-sharing/1.0

New key

The sender generates a content encryption key per file.

Encrypt & upload

The encrypted file goes to any server the recipient can reach. The server only ever sees ciphertext.

share-media

A normal DIDComm message carries the link and a ciphering block (algorithm, key, IV), end-to-end encrypted.

Fetch & decrypt

The receiver downloads and decrypts locally. (Its examples show no hash, which DIDComm v2 requires for linked attachments; worth adding.)

If the file is gone later, request-media (with the original thread as pthid) asks the sender to share it again.

large files

What changes when the file is gigabytes

  • Chunk it, with a hash per chunk, so a download can resume and corruption is caught early.
  • Encrypt per chunk too, so the receiver can decrypt as it goes instead of holding everything.
  • expires_time on the share message, matching how long the upload will be kept.
  • byte_count up front, so a phone on mobile data can wait for Wi-Fi.

a nice property

One upload, many recipients

The file is encrypted once, with its own key. Sharing with a group or with several devices means sending the small key in each recipient's DIDComm message, not re-uploading the file.

This fits nicely with multi-device (each device gets the key) and with fan-out group messaging (each member gets the key).

two different problems

Transfer is not storage

Transfer

Get this file from me to you, then the copy in the middle can go. That's what media-sharing/1.0 is for.

Storage

Keep this safe for years, let me grant and revoke access, survive a lost device. A much bigger design space.

storage in the registry

Two proposals for the storage side

vaults/1.0 · Proposed

DIDComm coordinates access to end-to-end encrypted data vaults on backends like S3 or Arweave: who gets access, to which objects, for how long. The bytes move over the vault's own HTTP API. Optional N-of-M threshold decryption.

swarm/1.0 · Proposed

Mediators and willing agents pledge to hold encrypted shards for a time, answer proof-of-storage challenges, and serve authorized retrievals. Aimed at durability: lost devices, crashed mediators, deleted CDN files.

Both keep DIDComm for coordination and keys, and move bulk data some other way.

the hard part

Sharing a key is forever

Once someone has a file's key and has downloaded the ciphertext, you can't un-share it. Revocation only works for future access.

  • Deleting the upload stops people who haven't fetched it yet.
  • Rotating to a new key means re-encrypting and re-uploading.
  • Access that expires needs something online to enforce it: a vault, a storage host, or a threshold of approvers.

metadata

What the storage host learns

Sizes

Exact ciphertext sizes can hint at what a file is. Padding helps.

Who and when

Upload and download times and IP addresses, i.e. who shared with whom.

Sameness

With content-derived names, identical files look identical. A fresh key per share avoids that.
