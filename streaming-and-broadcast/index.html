The gap · the invitation

The spec leaves the door open on purpose

This is a DIDComm messaging spec. Security, privacy, routing, and metadata concepts from this spec could be adapted to other communication styles, including multicast/broadcast and streaming. This will create sister specs to DIDComm Messaging, rather than evolving DIDComm Messaging itself.DIDComm Messaging v2.1 — Future Work, Beyond Messaging

The gap · why messaging isn't streaming

Every message stands alone

Each message MUST be transmitted individually; if encryption or signing are used, the unit of encryption or signing is one message only.Transports — WebSockets
  • Each message does its own key agreement and carries its own headers.
  • The libp2p transport extension runs DIDComm over a stream, but only as a pipe for separate messages.
  • Fine for chat. Too heavy for audio, video or high-rate telemetry.

The gap · what streaming needs

Low overhead

Small per-packet cost; no key agreement per chunk.

Low latency

Chunks usable as they arrive, not after the whole thing.

Loss tolerance

A dropped packet mustn't break everything after it, for live media.

Bounded memory

Encrypt and decrypt without holding the whole stream.

Two approaches · approach A

DIDComm sets it up; something else carries it

Use ordinary DIDComm messages to negotiate a stream: who, where, which cipher and a fresh session key. Then send the media over a transport built for it, encrypted with that key.

Good

Reuses DIDComm's identity, authentication and routing for the hard part. The stream layer can be an existing, well-tested protocol.

Costs

The stream no longer goes through mediators, so both ends must be reachable, and its security is only as good as how the key was handed over.

Two approaches · approach A, already proposed

webrtc/1.0 does this for calls

A registry protocol (status: Proposed) that uses DIDComm v2 as the signalling channel for WebRTC audio and video.

Identity-bound media

WebRTC's DTLS certificate fingerprints are bound to DID keys, against man-in-the-middle attacks.

Two topologies

Peer-to-peer mesh for small calls (2–8); an SFU for larger ones (10–100+).

End-to-end through an SFU

SFrame (RFC 9605) keeps media encrypted even when a server forwards it.

So for real-time media, the open question is less "how" and more "does this fit your use case". Non-media streams are still open.

Two approaches · approach B

Chunks as messages, with sequencing

Keep everything in DIDComm: each chunk is a message in one thread, with sender_order from the Advanced Sequencing extension so the receiver can reassemble and spot gaps.

Good

Works through mediators and offline transports. No new crypto.

Costs

Full envelope overhead on every chunk. Fine for "a large file, eventually"; poor for live media.

For large files specifically, attachments by reference (links + hash) avoid chunking altogether.

Beyond one-to-one · broadcast

One sender, many receivers

Public

Signed but not encrypted. Anyone can read; everyone can verify. The filesystem extension already describes a shared folder used this way.

Known audience

Encrypt for each recipient DID. Correct today, but the cost grows with the audience.

Large audience

A group key, rotated as members join and leave. The subject of a real multicast spec.

streaming and broadcast10 / 16
Beyond one-to-one · sessions

Streaming would add something messaging lacks

DIDComm messaging has no session construct, so the spec points to the DIDComm Guidebook for how forward secrecy maps onto it. A stream is a session by nature.

A sister spec could give streams forward secrecy by ratcheting the session key as the stream goes on. That's something one-shot messages can't easily do.

Beyond one-to-one · why anyone would want it

Use cases that don't fit one message at a time

Calls

Voice and video between parties who already have a DIDComm relationship.

Telemetry

A device reporting many times a second, where per-message envelopes dominate.

Announcements

An organisation broadcasting signed updates to everyone who follows it.

streaming and broadcast13 / 16
Beyond one-to-one · a caution

Don't reinvent media security

Real-time media encryption is a mature field with its own hard-won protocols. The most useful thing DIDComm can probably contribute is the part those protocols don't solve well: who you're talking to, and how to reach them. That's the split webrtc/1.0 makes.
