The gap · what goes in the push

The RFC leaves the payload mostly open

It requires @type. It allows message_tags and message_ids, so a push can point at the queued messages behind it.

Guidelines on notification messages are not defined.Aries RFC 0734 — Sending Push Notifications

That leaves two easy choices: a generic wake-up that says nothing, or message ids that travel through Google's infrastructure in plaintext.

A proposal: fcm-message

Specific and encrypted: a pointer to one message, in a push Google can't read.

A proposal · coordinate-mediation/3.1

One new message, sent by the mediator

A proposed, backward-compatible minor version of the Production coordinate-mediation/3.0. When the mediator queues a message instead of delivering it live, it may also send fcm-message.

It isn't sent over DIDComm's usual transport. The whole encrypted envelope rides, base64-encoded, as the data of the FCM push itself. No reply, no retry.

{
  "id": "123456780",
  "type": "https://didcomm.org/
    coordinate-mediation/3.1/fcm-message",
  "body": {
    "recipient_did": "did:peer:…",
    "message_id": "9f1c2e3a-…"
  }
}

Status: Proposed. Written as the real didcomm.org PIURI because the intent is to propose it upstream as exactly coordinate-mediation/3.1; until a registry PR merges, treat 3.1 as proposed, not adopted. return_route doesn't apply: there's no synchronous channel to reply on.
A proposal · what it's trying to do

Short, encrypted, and about one message

As short as possible

Two fields: which of the recipient's DIDs the message was queued under, and the queued message's id. Nothing about the sender or the content.

Encrypted in transit

A real authcrypt'd DIDComm message addressed to the recipient. FCM carries it but never sees even the opaque id in the clear, unlike a plaintext message_ids.

Points at one message

The app learns which queued message triggered this push, so it can go and get that message's body instead of treating the push as generic.

An optimization on top of pickup, never a replacement: if the push is lost, ordinary pickup still finds the message.

messagepickup/3.0 already calls a delivery attachment's id "an opaque value" the recipient "should not deduce any information from"; fcm-message uses the same id.
A proposal · staying inside the size budget

An envelope has to fit where a bare id did

FCM caps a payload at 4096 bytes, notification and data combined. An encrypted envelope is bigger than a bare id, and part of its size depends on how the recipient is addressed.

The long form grows

3.1 addresses the envelope with whatever form of the recipient's DID the mediator has on file. A did:peer:4 long form embeds the whole document, so it grows with the identity's device roster.

The short form doesn't

The short form is just a hash: constant size whatever the roster. The proposal lists short-form addressing as a future minor version.

did:peer method spec, numalgo 4: the short form is the hash of the long-form document; a party that already holds the long form can still resolve a message addressed to the short form.

Two paths to a message · why the ack matters

Delivered isn't the same as safe to delete

Delivered messages MUST NOT be deleted until delivery is acknowledged by a messages-received message.messagepickup/3.0 — Delivery Request

The ack is what lets either path fail safely. If the app is killed between ④ and ⑤, the messages are still queued, and the next pickup gets them again.

The same holds after a background fetch: until messages-received, the mediator still has the message.

Where decryption could happen · a spectrum, not a switch

Three places to draw the line

Never

The notification stays generic no matter what. Zero key material ever reaches the push path. Only the tap path is available.

While the process is alive

Decrypt only if the app hasn't been reclaimed by the OS yet. No new storage — the secret just lives in RAM, same as everything else running.

Even after it's killed

Decrypt from a wake-up alone, no running process required. Needs a secret that survives — real engineering, real new risk.

Nobody has to pick one tier for every user. It's a knob, not a verdict.

Where decryption could happen · the free middle tier

"While it's alive" costs almost nothing to build

Mirror the already-unlocked key into whatever process handles the push callback. Decrypt directly from there.

No new storage

The secret lives in ordinary process memory — nothing is written to disk that wasn't already there.

Self-expiring, for free

The OS reclaiming the process clears it automatically. True in any language, by construction, not a platform trick.

Where decryption could happen · the tier that costs something

"Even after it's killed" needs two different jobs done right

Confidentiality

Hardware-backed key storage (a secure element, not a derived value sitting in a file) — unextractable even from a rooted device.

Session binding

Tie it to one boot session, cryptographically — not a flag an attacker who already has the ciphertext could just set back.

A boot counter is public information — anyone can read it. It can only ever be a binding input (authenticated associated data on the cipher), never the secret itself. Easy mistake; worth naming.

Open questions

  • Should delivery-request be able to ask for one message by id, so the push path can fetch exactly what fcm-message names?
  • Should a recipient be able to opt out of fcm-message but keep the generic wake-up? Should the mediator know which tier a device picked?
  • Does encrypting an already-opaque id meaningfully change the privacy profile versus RFC 0734's plaintext message_ids?
  • Is there a cleaner way to bind a persisted secret to "this boot, this unlock" than a cipher's own authenticated data?
