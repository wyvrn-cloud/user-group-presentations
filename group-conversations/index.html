The starting point

DIDComm is pairwise; three shapes a group could take, and two that already exist.

The starting point · pairwise by rule

Encryption is per recipient DID, by rule.

A message being sent to multiple DIDs MUST be encrypted for each DID independently.DIDComm Messaging v2.1 — Message Encryption

One DID can have many keys (that's how multi-device works), but the core spec has no notion of a group as a recipient. Groups are left to protocols built on top, and the didcomm.org registry already has two quite different ones.

The starting point · three shapes

Ways a group could work

Pairwise fan-out

Every member sends each message to every other member over the pairwise channels they already have. No server, no new keys.

no registry protocol yet

A relay member

One party (a member or a service) receives and re-sends to everyone. Fewer sends from phones; one party sees who talks to whom.

group-chat/1.0

A shared group key

Encrypt once for the group, e.g. with an MLS tree. Cheap sends; membership changes need careful coordination.

rooms/1.0

The starting point · already in the registry

Two existing takes, at opposite ends

group-chat/1.0 · Demonstrated

An administrator's controller agent invites participants and forwards each group message to every active participant. Participants only need a connection to the controller, not to each other, and see each other by pseudonymous alias.

rooms/1.0 · Demonstrated

MLS (RFC 9420) for group keys, a Host that orders handshakes and fans out, optional routers for mesh relay. DIDComm supplies addressing, routing, threading and mediation.

Neither is the fully serverless, every-member-talks-to-every-member shape. That's the gap the fan-out approach explores.

Fan-out: N−1 ordinary messages

This is the shape explored in the group-chat notes in wyvrn-cloud/protocols, an experiment rather than a standard.
Fan-out · membership

Who is in the group? Everyone keeps their own list.

  • invite: sent to a new member with the current member list.
  • member-added: sent to existing members so their lists stay in step.
  • No group server and no shared state: each member's view is their own record of who they've been told is in.

The hard parts

Who may add members? Is there consent to join? How does someone leave, or get removed? What if two members' lists disagree? A minimal design can leave all of these open, but a real deployment can't.

Fan-out · ordering

More than two parties means ordering gets ambiguous

The spec's Advanced Sequencing extension exists for exactly this. It detects gaps and reordering; it deliberately doesn't say how to fix them.

  • sender_order: my 1st, 2nd, 3rd message in this thread.
  • sent_count: how many I've sent, including resends.
  • received_orders: the highest I've seen from each party, and any gaps.
"received_orders": [
  { "id": "did:ex:bob",
    "last": 2, "gaps": [] },
  { "id": "did:ex:alice",
    "last": 4, "gaps": [2,3] }
]

Fan-out · threads

Existing threading covers more than it seems

thid

A natural fit for "this group conversation", so every member files the message in the same place.

pthid

For side interactions spawned from the group, like a poll or a file transfer. With more than two parties, the spec requires each party to learn the parent from the first child message they see.

A shared key · the other end of the spectrum

A shared group key, MLS-style

MLS (RFC 9420) keeps a tree of keys so a group can agree on a shared secret. Its tree lets a member encrypt to everyone but one "with a number of ciphertexts that is logarithmic in the number of group members", which is what makes removals and key updates cheap. rooms/1.0 layers exactly this on DIDComm.

What it buys

One encryption per message, however big the group. Forward secrecy and recovery after a member's device is compromised.

What it asks for

Membership changes must be applied in the same order by everyone, so something has to order them. In rooms/1.0 that's the Host, acting as the MLS delivery service.

What's left · not solved by the simple version

The parts a real group protocol needs

  • Leaving and removal, and what the removed member can still see.
  • Consent: accepting or declining an invite, not auto-joining.
  • Roles: can any member add anyone?
  • Read receipts: "seen by 3 of 5" is not the pairwise receipts/1.0.
  • History for new members (see "Catching Up a New Device").
  • Groups whose members have many devices each.

What's left · it composes

Multi-device and groups multiply

With per-device keys, a message to a 5-person group where everyone has 3 devices is 4 envelopes (one per other member's DID) with 3 key wraps in each. Content is encrypted once per envelope; only the small content key is wrapped per device.

The spec calls this "multiplexed encryption": encrypt the content once, then wrap the ephemeral content key for each recipient key.

group conversations15 / 17
Spec: Routing, DID Document Keys — "DIDComm encrypts the main message content only once, using an ephemeral content encryption key, and then encrypts the relatively tiny ephemeral key once per recipient key." Holds when all of a recipient's keys are the same type.
