Sensors, meters and gateways: devices that sleep, have little memory and slow links. What the spec already offers them, and where it gets heavy.

what's different

IoT devices break the phone-and-server assumptions

Asleep

Awake for seconds, then gone for minutes or hours to save battery.

Small

Kilobytes of RAM, not gigabytes. Big messages may not fit in memory at all.

Slow links

Low-power radios where every byte costs airtime and energy.

Headless

No screen, no person to scan a QR or approve a prompt.

devices that sleep

Let something else stay awake

A mediator holds mail

Messages queue at the mediator; the device picks them up when it wakes.

Queue transport

The return-route extension's didcomm:transport/queue: messages wait at the sender until the device connects and collects them.

Return route

The device opens the connection when awake and asks for replies over it with return_route.

expires_time lets senders say when a queued command is no longer worth delivering.

a common shape

One gateway, many devices

Each device has its own DID; the gateway is its mediator. End-to-end encryption means the gateway forwards messages it can't read. The registry's mesh/1.0 describes gateways that do exactly this for BLE and LoRa clusters.

where it gets heavy

Full compliance asks a lot of a microcontroller

Key agreement

X25519, P-384 and P-256 are all MUST-support curves, plus AES-256-CBC with HMAC-SHA512 for authcrypt.

Signatures

Implementations MUST be able to verify EdDSA (Ed25519), ES256 and ES256K. (JOSE has since deprecated the generic EdDSA identifier in favour of fully-specified ones like Ed25519: RFC 9864.)

A tiny device that only ever talks to its own gateway doesn't need all of that. Is there room for a constrained profile: one curve, one cipher, declared up front?

identity for devices

Provisioning, rotation, retirement

Provision

At install, an out-of-band invitation (printed QR on the device, or pushed by the installer's phone) sets up the first relationship.

Rotate

Switch to a relationship-specific DID with from_prior, signed by the previous DID's key.

Retire

End the relationship by rotating to nothing: a from_prior with no sub.

A printed QR code is public forever. The spec says identifiers passed that way should be rotated if privacy matters.

one-way devices

A sensor that never listens

DIDComm transports are simplex by design; HTTPS delivery is a one-way POST. A device that only ever sends is still a legitimate DIDComm sender.

  • It still needs a DID the recipient can resolve, to authenticate its messages.
  • It can't receive problem reports or acknowledgements, so delivery is best-effort.
  • Key rotation has to be driven from the device side, or not at all.

size

Every byte is airtime

In the spec's own test vectors, a 241-byte plaintext becomes 1,430 bytes authcrypted to three X25519 keys, and 3,381 bytes when signed, authcrypted and then anoncrypted to hide the sender.

Batch

Send readings in batches, using attachments or an array body, so the envelope cost is shared.

Encode differently

A binary profile would help most here (see "DIDComm in CBOR?"), or a compact link-level envelope like mesh/1.0's.

why bother

What DIDComm offers over "just MQTT and TLS"

End-to-end

Security survives gateways, brokers and store-and-forward hops, not just one TLS connection.

Portable identity

A device's DID isn't tied to one vendor's cloud account.

Transport-agnostic

The same message can go over a local radio, a gateway, or HTTPS.
