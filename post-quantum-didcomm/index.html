The designers of DIDComm are aware that DIDComm's cryptographic methods will need to be upgraded when quantum computing matures. The threat · why now, not later

Harvest now, decrypt later

An encrypted DIDComm message captured today, at a mediator, in a log or on the wire, can be stored and decrypted once the capability exists. Confidentiality is the urgent part.

Urgent: key agreement

Protects content that must stay secret for years: health, legal, commercial.

Less urgent: signatures

A signature only needs to resist forgery until it is checked, unless it's long-term evidence.

The threat · what exists now

NIST published the first standards in 2024

ML-KEM — FIPS 203

Key encapsulation (from Kyber). The replacement for ECDH key agreement.

ML-DSA — FIPS 204

Signatures (from Dilithium). General-purpose replacement for EdDSA/ECDSA.

SLH-DSA — FIPS 205

Hash-based signatures (from SPHINCS+). Larger, slower, very conservative assumptions.

ML-DSA is now registered for both JOSE and COSE (RFC 9964). ML-KEM is still in IETF drafts (e.g. draft-ietf-jose-pqc-kem). Nothing yet for DIDComm itself.

What changes · the second surprise

Some DIDs contain their keys

did:peer method 2 encodes the keys in the DID string itself; method 4's long form encodes the whole document. With post-quantum keys, those identifiers grow to kilobytes.

  • They appear in every message's from and to headers.
  • They don't fit comfortably in a QR code for out-of-band invitations.
  • Identifiers that don't embed keys fare better: did:peer:4's short form (a hash of the long form, usable after the first exchange), or ledger and web methods.

What changes · the deeper problem

Authcrypt is built on Diffie-Hellman

ECDH-1PU authenticates the sender by mixing the sender's static key into the key agreement. A KEM isn't Diffie-Hellman: it encapsulates a secret to one public key, and there's no direct "one-pass unified model" equivalent.

Sign, then encrypt

Works today with a PQ signature, but gives up authcrypt's deniability, and signatures are large.

Authenticated KEM designs

An active research area. Not yet something to standardize on.

Getting there · a pragmatic step

Hybrid: classical and post-quantum together

Derive the key-wrapping key from both an X25519 exchange and an ML-KEM encapsulation. An attacker has to break both.

Why

Protects against harvest-now-decrypt-later while keeping today's security if the new algorithm turns out to be weak. An IETF draft defines exactly this for TLS 1.3 as X25519MLKEM768.

How it could show up

A new key-wrapping algorithm, recipient keys that carry both public keys, and a new profile in the accept list.

Getting there · migration

Rotation is signed with the key being retired

from_prior is a JWT signed by a key the old DID authorizes. Once that key type can be broken, anyone could forge a rotation from your old DID to theirs.

  • Relationships should migrate to post-quantum DIDs before the old keys become breakable.
  • Afterwards, receivers must stop accepting rotations signed with the old algorithms.
  • Long-lived evidence signed with old algorithms may need re-signing or timestamping.

Getting there · already proposed

pq-bridge/1.0: post-quantum on top, not inside

A registry protocol (status: Proposed) that adds ML-KEM and ML-DSA after a normal DIDComm connection exists, as a transitional layer until the core envelopes adopt them.

Ephemeral PQ DIDs

Each session gets a fresh did:peer:4 holding the PQ keys, so long-lived DID documents never carry them.

Hybrid modes

X25519 + ML-KEM and Ed25519 + ML-DSA, negotiated with Discover Features.

Wrapped bodies

Message bodies and attachments are wrapped in a PQ envelope, with replay protection and key rotation.

It sidesteps the big-DID problem from earlier, at the cost of a second envelope layer and a session to manage.

Getting there · what's already flexible

The spec's extension points help

DID methods

Any DID method can publish new key types; DIDComm doesn't hard-code where keys come from.

Profiles

A new profile string in accept lets endpoints advertise PQ support without breaking others.

Multiple keys

A DID document can list classical and PQ keys side by side during a transition.
