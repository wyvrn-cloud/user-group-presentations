The problem · hard to hand out

A did:peer:4 is the wrong shape for a profile

Long

The long form carries the whole document: 806 characters for one device's keys in our measurements. Not something to say aloud, print, or send in a text.

Changes

It's a hash of its document, so every key change is a new DID. Add a phone and everyone you gave the old one to has a stale address.

Private by design

It works between two parties who already met. Someone you haven't met has nowhere to look it up.

People and services that are public on purpose need a second DID: short, stable, and resolvable by anyone.

The problem · what's close, and why it isn't this

Three near misses

shorten-url/1.0

Shortens one link, usually an invitation. The short URL is a redirect its operator controls: nothing about it can be verified, and it isn't an identifier.

did:web

Short and readable. But it has no history and no signature: it is whatever the web server says today.

did:webvh

Exactly the identifier wanted: readable, resolvable over HTTPS, with a signed history the server can't forge. But it needs a web server the agent can write to, and a phone has none.

So: let an agent that can't host a file have one hosted, without giving the host any say over what the file says.

did:webvh · a web DID with a history

did:webvh:QmfGEUAc…XQ:id.example:alice

  • The DID's history is a log, did.jsonl: one JSON entry per version.
  • Each entry is signed by a key the entry before it allowed (updateKeys).
  • The SCID in the DID is a hash of the first entry, so a different log is a different DID.
  • It can be published beside a parallel did:web derived from it.
  • A whois.vp beside the log says who the DID is, signed by it.
  • Optional: portable to move hosts, pre-rotation, witnesses and watchers.

A host that can't change anything · who does what

Three roles, and only one holds keys

Holder

Writes its own did:webvh log and signs every entry. The DID's controller in every sense the method means.

Host

Checks each entry, stores it, serves it over HTTPS with the parallel did:web. Holds none of the holder's keys.

Admin

Decides who may claim a name that's been set aside. Never writes, signs or uploads anybody's log.

The worst a host can do is stop serving a DID, or keep serving an old version. It can't change where the DID points or read what is sent to it.

A host that can't change anything · names

A name is a path at the host

The DIDdid:webvh:<SCID>:id.example:alice
Its loghttps://id.example/alice/did.jsonl
Its parallel did:webdid:web:id.example:alice, at /alice/did.json
Its whoishttps://id.example/alice/whois.vp

Plain labels only

3 to 32 of a–z, 0–9 and -. No capitals, no other scripts: names that look alike are alike, so there's no look-alike of someone else's.

First come, except reserved

A reserved name, or any name under a reserved namespace like official, can be claimed only by the holder an admin assigns it to.

A host that can't change anything · getting one

Alice gets a public address

Reserve

reserve alice. The host holds it briefly, and says the did:web it will be.

Name it

Her did:peer:4 adds the did:web to its alsoKnownAs: a new DID, rotated to contacts as usual.

Write

The first log entry: the same keys and endpoint as her did:peer:4, naming both.

Publish

publish with the entry attached and signed. The host checks it, then serves it.

Say who

publish-whois: her profile, as a signed presentation.

Later she adds a tablet: either device appends an entry, and the address doesn't change. Nobody she gave it to has to be told.

Why the did:web goes into the did:peer:4 and not the did:webvh: the did:webvh's SCID is a hash of the log's first entry, which itself names the did:peer:4. The did:web is the one name known before the log exists. Reserving first matters for the same reason: the name has to be held before the identity names it.

Each names the next, and the circle closes

A pair is accepted only if each names the other back; a did:web that points at a did:webvh which doesn't name it back gains nothing.

The protocol · the messages

Nine messages, mostly small

Holderreserve → reservation
publish → published
publish-whois → status
Anyonestatus-request → status
Adminassign, free

Every message must be authcrypted, and every attachment carries a detached signature (data.jws) by the DID's own authentication key.

{
  "type": ".../did-hosting/1.0/publish",
  "body": {
    "name": "alice",
    "after": "3-QmQq6K…"
  },
  "attachments": [{
    "id": "log",
    "media_type": "text/jsonl",
    "data": {
      "base64": "eyJ2ZXJzaW9uSWQ…",
      "jws": { … }
    }
  }]
}

Plus a standard report-problem/2.0 problem-report with codes like name-taken, name-reserved, not-held, log-invalid, conflict, key-in-use. "after" is the versionId of the last hosted entry the new entries follow; absent on a first publication, where the attachment is the whole log. Over HTTP a message that isn't authcrypted is answered 403: there is nobody to send a problem-report to.
The protocol · what a host checks

Seven checks on every publish, against the whole log

  • The log is valid did:webvh 1.0: SCID, entry hashes, every proof.
  • It continues what's hosted, never replaces it.
  • The document's id is this name's DID.
  • Its alsoKnownAs names the parallel did:web.
  • The sender wrote with a keyAgreement key of the document, and signed with an authentication key.
  • None of its keys has been shown to belong to a DID under another name.
  • The name may be claimed by this sender: held for it, or assigned to it.

A host should also require portable: true in the first entry, so the holder can leave with its history.

The protocol · who a sender is

Known by the key it wrote with, not by its DID

The holder's did:peer:4 changes between reserving and publishing, and with every device after. And a did:peer:4 can list anyone's public key. So a host looks only at the key that authenticated the message.

A hold

Is for the key that asked. The publish must come from the same key.

One name per holder

A key shown to be a holder's (by acting as it, not by being listed) can't take a second name, in any version of the log.

Two devices at once

Both append; the first wins. The second's after is stale, so it gets conflict, rebuilds on top, and publishes again.

a did you can give out14 / 24
"Shown to be, not merely listed": a document can list someone else's public key, and that must not use the key up. A key counts once its owner acts as the holder with it (a publish or publish-whois authenticated with it or signed by it, or a status-request naming the name) while the name's document lists it. This makes each name cost a new identity; it doesn't stop someone making new keys.

Reading one · resolving

Move from the did:web to the did:webvh at once

Resolve the did:web

If its alsoKnownAs names a did:webvh, resolve and verify that log.

Check it names you back

Accept the pair only if the did:webvh lists the did:web. Otherwise the did:web stands alone.

Keep the did:webvh

Know the party by it from then on.

A reassigned name is someone else

If a name is freed and claimed afresh, the same did:web now leads to a did:webvh with a different SCID. An app must treat that as a different party, and say so.

Reading one · who they say they are

A profile the DID signs, and two ways to trust it more

The whois

A Linked Verifiable Presentation holding a profile credential the DID issues about itself: schema.org name, description, image. Its own word, nothing more.

A linked domain

A LinkedDomains service names a website, and the website serves a DID Configuration naming the DID back. Checked when asked, and remembered.

A namespace you know

An app may treat a reserved namespace at a host it knows as a mark by itself, for example official.

An app should always show the host and the name beside a profile: alice is just whoever asked first.

One experiment · with several devices

Nothing about the address lives on one device

It rides on the identity

That there's an address is in the Identity DID's alsoKnownAs, which every device already holds. Nothing else is stored.

Every trusted device can write

The log's updateKeys are the document's authentication keys: each trusted device's own. Trusting a device lets it write; revoking it stops it.

It follows every roster change

After a device is added, removed or trusted, each trusted device fetches the log and appends if needed. The first wins; the rest find it written.

So no single device's loss strands the address, as long as one trusted device remains.

a did you can give out20 / 24
This ties to "DIDComm for People": the address's document is the Identity DID's own under the address's name, so every rotation of the Identity DID is followed by a log entry. The app reads the writers from the document, never from the device roster: the roster is patched at a different moment than the identity rotates, and a list taken from it in between once had a newly trusted device write itself out of the log.
One experiment · quiet holders, and the end

Silence means nothing, so the host asks

Stale

A holder that never changes devices never writes again. After a year without hearing from it, the host sends a trust-ping; a week with no answer makes the name stale: still served, and one an admin may free.

Ended

A holder ends its DID the did:webvh way: an entry with deactivated: true. The host keeps serving the log, so the end is itself verifiable.

One experiment · what it doesn't do yet

The gaps, plainly

  • The host can withhold. It can serve an old version and no one can tell. No witnesses or watchers yet.
  • No pre-rotation. nextKeyHashes isn't used.
  • The host learns who resolves, by IP address. An app may resolve through a proxy.
  • No rate limits in the host itself.
  • No recovery. Lose every trusted device and the DID can never be updated again; an offline recovery key in updateKeys would be a way back.
  • Moving hosts is possible with portable, but what the old host serves afterwards isn't defined.

Everything published is public, including the link between this name and the identity behind it. An app should make sure the person knows before publishing.
