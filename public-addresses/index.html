The problem

A good DID for a relationship is a poor one to hand out.

The problem · hard to hand out

did:peer DIDs are incredibly long, and aren't user-friendly things to share

Long

The long form carries the whole document: 806 characters for one device's keys in our measurements. Not something to say aloud, print, or send in a text.

Changes

It's a hash of its document, so every key change is a new DID. Add a phone and everyone you gave the old one to has a stale address.

Private by design

It works between two parties who already met. Someone you haven't met has nowhere to look it up.

People and services that are public on purpose need a second DID: short, stable, and sharable by anyone.

The problem · what's close, and why it isn't this

Three near misses

shorten-url/1.0

Shortens one link, usually an invitation. The short URL is a redirect its operator controls: nothing about it can be verified, and it isn't an identifier.

did:web

Short and readable. But it has no history and no signature: it is whatever the web server says today.

did:webvh

Exactly the identifier wanted: readable, resolvable over HTTPS, with a signed history the server can't forge. But it needs a web server the agent can write to, and a phone has none.

So: let an agent that can't host a file have one hosted, without giving the host any say over what the file says.

did:webvh, briefly

The parts of the method this approach leans on, and how a name maps onto it.

public addresses4 / 24
did:webvh · a web DID with a history

did:webvh:QmfGEUAc…XQ:id.example:alice

  • The DID's history is a log, did.jsonl: one JSON entry per version.
  • Each entry is signed by a key the entry before it allowed (updateKeys).
  • The SCID in the DID is a hash of the first entry, so a different log is a different DID.
  • It can be published beside a parallel did:web derived from it.
  • A whois.vp beside the log says who the DID is, signed by it.
  • Optional: portable to move hosts, pre-rotation, witnesses and watchers.

did:webvh · names

A name is a path at the host

The DIDdid:webvh:<SCID>:id.example:alice
Its loghttps://id.example/alice/did.jsonl
Its parallel did:webdid:web:id.example:alice, at /alice/did.json
Its whoishttps://id.example/alice/whois.vp

Plain labels only

3 to 32 of a–z, 0–9 and -. No capitals, no other scripts: names that look alike are alike, so there's no look-alike of someone else's.

First come, except reserved

A reserved name, or any name under a reserved namespace like official, can be claimed only by the holder an admin assigns it to.

A host that can't change anything · who does what

Three roles, and only one holds keys

Holder

Writes its own did:webvh log and signs every entry. The DID's controller in every sense the method means.

Host

Checks each entry, stores it, serves it over HTTPS with the parallel did:web. Holds none of the holder's keys.

Admin

Decides who may claim a name that's been set aside. Never writes, signs or uploads anybody's log.

The worst a host can do is stop serving a DID, or keep serving an old version. It can't change where the DID points or read what is sent to it.

public addresses8 / 24
A host that can't change anything · getting one

Alice gets a public address

Reserve

reserve alice. The host holds it briefly, and says the did:web it will be.

Name it

Her did:peer:4 adds the did:web to its alsoKnownAs: a new DID, rotated to contacts as usual.

Write

The first log entry: the same keys and endpoint as her did:peer:4, naming both.

Publish

publish with the entry attached and signed. The host checks it, then serves it.

Say who

publish-whois: her profile, as a signed presentation.

Later she adds a tablet: either device appends an entry, and the address doesn't change. Nobody she gave it to has to be told.

public addresses9 / 24
Why the did:web goes into the did:peer:4 and not the did:webvh: the did:webvh's SCID is a hash of the log's first entry, which itself names the did:peer:4. The did:web is the one name known before the log exists. Reserving first matters for the same reason: the name has to be held before the identity names it.
A host that can't change anything · three DIDs, one party

Each alsoKnownAs points at each other to solidify trust

A pair is accepted only if each names the other back; a did:web that points at a did:webvh which doesn't name it back gains nothing.

public addresses10 / 24
A message from the did:peer:4 is from the address's holder if the did:peer:4's own document lists the did:web in alsoKnownAs and shares a keyAgreement key with the did:webvh document. The did:webvh document also lists the did:web back, as every hosted DID must. Arrows show "names in alsoKnownAs"; the did:webvh also names the did:web back.

The protocol

did-hosting/1.0: reserving, publishing, and what a host checks.

public addresses11 / 24
The protocol · the messages

Nine messages, mostly small

Holderreserve → reservation
publish → published
publish-whois → status
Anyonestatus-request → status
Adminassign, free

Every message must be authcrypted, and every attachment carries a detached signature (data.jws) by the DID's own authentication key. Press ↓ for an example of each.

{
  "type": ".../did-hosting/1.0/publish",
  "body": {
    "name": "alice",
    "after": "3-QmQq6K…"
  },
  "attachments": [{
    "id": "log",
    "media_type": "text/jsonl",
    "data": {
      "base64": "eyJ2ZXJzaW9uSWQ…",
      "jws": { … }
    }
  }]
}
public addresses12 / 24
Plus a standard report-problem/2.0 problem-report with codes like name-taken, name-reserved, not-held, log-invalid, conflict, key-in-use. "after" is the versionId of the last hosted entry the new entries follow; absent on a first publication, where the attachment is the whole log. Over HTTP a message that isn't authcrypted is answered 403: there is nobody to send a problem-report to.
The protocol · reserve

reserve holder → host

{
  "type": ".../did-hosting/1.0/reserve",
  "body": {
    "name": "alice"
  }
}

Asks for a name to be held.

  • The hold is for the key the message was authcrypted with: the publish must come from the same one.
  • A sender has at most one hold; a new reserve replaces it.
public addresses · the messages12.1
Refused with name-invalid, name-taken, name-reserved or key-in-use (the sender already holds another name).
The protocol · reservation

reservation host → holder

{
  "type": ".../did-hosting/1.0/reservation",
  "thid": "<reserve id>",
  "body": {
    "name": "alice",
    "host": "id.example",
    "did_web": "did:web:id.example:alice",
    "expires_time": 1791727200
  }
}

The name is held, for a short while.

  • did_web is the one name known now: the identity adds it to its alsoKnownAs next.
  • There is no did:webvh yet: it doesn't exist until the log is written.
  • Publish before expires_time, or the name goes back.

The protocol · publish

publish holder → host

{
  "type": ".../did-hosting/1.0/publish",
  "body": {
    "name": "alice",
    "after": "3-QmQq6K…"
  },
  "attachments": [{
    "id": "log",
    "media_type": "text/jsonl",
    "data": {
      "base64": "eyJ2ZXJzaW9uSWQ…",
      "jws": { … }
    }
  }]
}

Publishes a DID, or adds to one.

  • after: the last hosted entry this follows. Absent the first time, when the attachment is the whole log.
  • The attachment is the new log entries, one per line, oldest first.
  • jws: a detached signature by an authentication key of the newest document.

A stale "after" gets a problem-report with conflict, carrying the real last versionId; the device rebuilds its entry on top and tries again.
The protocol · published

published host → holder

{
  "type": ".../did-hosting/1.0/published",
  "thid": "<publish id>",
  "body": {
    "name": "alice",
    "did": "did:webvh:QmfGEU…:id.example:alice",
    "did_web": "did:web:id.example:alice",
    "version_id": "1-QmQq6Kg4…"
  }
}

The DID now exists, and is served.

  • did: the first time the holder sees its did:webvh confirmed by the host.
  • version_id: what the next publish puts in after.

The protocol · publish-whois

publish-whois holder → host

{
  "type": ".../did-hosting/1.0/publish-whois",
  "body": { "name": "alice" },
  "attachments": [{
    "id": "whois",
    "media_type": "application/vp",
    "data": {
      "base64": "eyJAY29udGV4dCI6…",
      "jws": { … }
    }
  }]
}

Sets, or removes, the profile beside the log.

  • The attachment is a signed Verifiable Presentation: the profile credential the DID issues about itself.
  • The host checks the jws, that the presentation's holder is the hosted DID, its proof, and that a credential is about that DID.
  • No attachment removes the whois.

The protocol · status-request

status-request anyone → host

{
  "type": ".../did-hosting/1.0/status-request",
  "body": {
    "name": "alice"
  }
}

Asks what state a name is in.

  • name is optional: without it, the host answers for the name the sender holds.
  • A holder's new device sends one once. That is what shows its key is the holder's, so it can't claim a second name.
public addresses · the messages12.6
The protocol · status

status host → anyone

{
  "type": ".../did-hosting/1.0/status",
  "thid": "<status-request id>",
  "body": {
    "name": "alice",
    "state": "published",
    "did": "did:webvh:QmfGEU…:id.example:alice",
    "version_id": "1-QmQq6Kg4…",
    "whois": true,
    "yours": false
  }
}

Where a name stands.

  • state: free, reserved, held, published, stale or deactivated.
  • yours: whether the sender is the holder, or the one it's held for or assigned to.
  • It never tells anyone but an admin who a reserved name is assigned to, or who holds a hold.

The protocol · assign

assign admin → host

{
  "type": ".../did-hosting/1.0/assign",
  "body": {
    "name": "official:announcements",
    "holder": "did:peer:4zQmd8Cp…"
  }
}

Says who may claim a reserved name.

  • name can be a namespace, official:*, to reserve every name under it.
  • holder null reserves the name for nobody.
  • The assigned holder then reserves and publishes like anyone. An admin never writes the DID.
public addresses · the messages12.8
The protocol · free

free admin → host

{
  "type": ".../did-hosting/1.0/free",
  "body": {
    "name": "alice",
    "comment": "Holder unreachable since 2025-10."
  }
}

Ends a DID's hosting, and releases the name.

  • The host stops serving the log, the did.json and the whois.
  • The name goes back to free, or reserved if it's on the host's list.
  • Anyone who kept the old did:webvh must treat a new holder as someone else.

The protocol · problem-report

problem-report host → sender

{
  "type": "https://didcomm.org/report-problem/2.0/problem-report",
  "pthid": "<publish id>",
  "body": {
    "code": "e.p.msg.conflict",
    "comment": "The log has moved on: its last entry is {1}.",
    "args": ["3-QmQq6K…"]
  }
}

Every refusal, in the standard form.

  • A standard report-problem/2.0, its pthid the message it refuses.
  • Codes include name-taken, name-reserved, not-held, log-invalid, conflict, key-in-use and too-large.
  • A message that isn't authcrypted gets nothing: over HTTP, a 403.

The protocol · what a host checks

Seven checks on every publish, against the whole log

  • The log is valid did:webvh 1.0: SCID, entry hashes, every proof.
  • It continues what's hosted, never replaces it.
  • The document's id is this name's DID.
  • Its alsoKnownAs names the parallel did:web.
  • The sender wrote with a keyAgreement key of the document, and signed with an authentication key.
  • None of its keys has been shown to belong to a DID under another name.
  • The name may be claimed by this sender: held for it, or assigned to it.

A host should also require portable: true in the first entry, so the holder can leave with its history.

The protocol · who a sender is

Known by the key it wrote with, not by its DID

The holder's did:peer:4 changes between reserving and publishing, and with every device after. And a did:peer:4 can list anyone's public key. So a host looks only at the key that authenticated the message.

A hold

Is for the key that asked. The publish must come from the same key.

One name per holder

A key shown to be a holder's (by acting as it, not by being listed) can't take a second name, in any version of the log.

Two devices at once

Both append; the first wins. The second's after is stale, so it gets conflict, rebuilds on top, and publishes again.

public addresses14 / 24
"Shown to be, not merely listed": a document can list someone else's public key, and that must not use the key up. A key counts once its owner acts as the holder with it (a publish or publish-whois authenticated with it or signed by it, or a status-request naming the name) while the name's document lists it. This makes each name cost a new identity; it doesn't stop someone making new keys.

Resolving more than just a DID

From a short did:web to a verified DID and a profile, before sending anything.

public addresses15 / 24
Resolving more than just a DID · resolving

Move from the did:web to the did:webvh at once

Resolve the did:web

If its alsoKnownAs names a did:webvh, resolve and verify that log.

Check for cross-referencing

Accept the pair only if the did:webvh lists the did:web. Otherwise the did:web stands alone.

Keep the did:webvh

Know the party by it from then on.

A reassigned name is someone else

If a name is freed and claimed afresh, the same did:web now leads to a did:webvh with a different SCID. An app must treat that as a different party, and say so.

Resolving more than just a DID · who they say they are

A profile the DID signs, and two ways to trust it more

The whois

A Linked Verifiable Presentation holding a profile credential the DID issues about itself: schema.org name, description, image. Its own word, nothing more.

A linked domain

A LinkedDomains service names a website, and the website serves a DID Configuration naming the DID back. Checked when asked, and remembered.

A namespace you know

An app may treat a reserved namespace at a host it knows as a mark by itself, for example official.

An app should always show the host and the name beside a profile: alice is just whoever asked first.

Pictures: the profile picture should be a data: URL so showing it fetches nothing (the wyvrn host allows 64 KB); larger pictures may be https: URLs but must carry a sha256, and shouldn't be fetched until someone opens the profile, since fetching tells the picture's host who's looking. The one non-schema.org term is wyvrn's background, kept under a "wyvrn" @nest. Linked domains follow DIF Well Known DID Configuration, eddsa-jcs-2022 proofs, checked against the document's assertionMethod keys.

A host, a shared reader, and an app on both ends

The host

services/did-host (wyvrn-did-host): names, holds, the seven checks, the parallel did:web and whois, admin commands, staleness.

One reader, two places

crates/wyvrn-hosted-did decides what a hosted DID comes to from bytes it's handed; the caller fetches. The host's tests run it, and so does the app, as wyvrn-hosted-did-wasm on the web.

The app

src/services/hostedDid and hosted_did.rs in wyvrn-chat: getting an address, keeping it in step, looking one up, linking a website.

Verifying the log

DIF's own didwebvh-rs (0.8), in the host, the reader, and wyvrn-didcomm's didcomm-resolver-webvh.

Marked experimental and not live: run on a phone against a host on a test machine.

An implementation · with several devices

Nothing about the address lives on one device

Named by the identity

The Identity DID's alsoKnownAs names the address. Every device already holds that DID, so every device knows the address without keeping a record of its own.

Every trusted device can write

The log's updateKeys are the document's authentication keys: each trusted device's own. Trusting a device lets it write; revoking it stops it.

It follows every roster change

After a device is added, removed or trusted, each trusted device fetches the log and appends if needed. The first wins; the rest find it written.

So no single device's loss strands the address, as long as one trusted device remains.

public addresses20 / 24
This ties to "DIDComm for People": the address's document is the Identity DID's own under the address's name, so every rotation of the Identity DID is followed by a log entry. The app reads the writers from the document, never from the device roster: the roster is patched at a different moment than the identity rotates, and a list taken from it in between once had a newly trusted device write itself out of the log.
An implementation · quiet holders, and the end

Silence means nothing, so the host asks

Stale

A holder that never changes devices never writes again. After a year without hearing from it, the host sends a trust-ping; a week with no answer makes the name stale: still served, and one an admin may free.

Ended

A holder ends its DID the did:webvh way: an entry with deactivated: true. The host keeps serving the log, so the end is itself verifiable.

An implementation · what it doesn't do yet

Improvements that haven't been implemented

ImprovementWhat it would fix
Witnesses and watchersA host serving an old version of the log, which today nobody would notice.
Pre-rotation (nextKeyHashes)A stolen signing key writing keys of its own into the next entry.
An offline recovery key in updateKeysLosing every trusted device, which today leaves the DID frozen for good.
A rule for moving hostsportable makes a move possible; what the old host serves afterwards isn't defined.
Rate limits in the hostFloods and name-grabbing. Today a rate limit has to sit in front of it.
Resolving through a proxyThe host learning, by IP address, who looks an address up.

One thing no improvement changes: everything published is public, including the link between this name and the identity behind it. An app should make sure the person knows before publishing.
