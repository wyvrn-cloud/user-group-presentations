the starting point

basicmessage/2.0 is deliberately basic

{
  "id": "123456780",
  "type": "https://didcomm.org/basicmessage/2.0/message",
  "lang": "en",
  "created_time": 1547577721,
  "body": {
    "content": "Your hovercraft is full of eels."
  }
}

One field of text. Its own endnotes list what it leaves out on purpose:

  • read receipts
  • emoji responses
  • typing indicators
  • message replies (threading)
  • multi-party (group) messages

"We anticipate the development of more advanced and full-featured message protocols to fill these needs."

The feature list of any modern chat app

Structure

Replies, quoted messages, threads within a conversation.

An emoji on someone else's message, added and removed.

Changes

Edit a sent message. Delete it, for yourself or for everyone.

Presentation

Bold, italics, underline, code, links, mentions, embedded media and previews.

what DIDComm already gives you

Unique message ids

Every message has an id unique across the parties' interactions: a stable handle for replying to, reacting to, editing or deleting it.

Threads

thid and pthid. But these mean protocol interactions; reusing them for UI threads needs care.

receipts/1.0

A registry protocol for received, viewed and deleted states, requested per message type.

Attachments

Inline or by reference with a hash: the natural carrier for images, files and previews.

replies and threads

Two ways to say "this answers that"

Reuse thid

Set the reply's thid to the original message's id. No new fields, but it overloads a header that protocols use to track their own state. A reply to a reply to a reply becomes ambiguous.

A body field

Something like reply_to: "<message id>", plus an optional thread root for sub-threads. Explicit, and leaves DIDComm threading alone.

Other messaging systems chose the second: Matrix uses relations on the event (m.in_reply_to, m.thread); XMPP has a separate extension for replies (XEP-0461).

reactions

A tiny message that points at another

{
  "type": ".../reaction",   // hypothetical
  "body": {
    "target": "<message id>",
    "reactions": ["👍", "🎉"]
  }
}
  • Send the full set each time, not "add" and "remove". Then a lost or reordered message can't leave a stale reaction behind. XMPP's reactions extension (XEP-0444) works this way.
  • In groups, every member's set must reach every member, which multiplies with fan-out.
  • Should a reaction request a receipt? Probably not.

edits and deletes

You can't take back what's been delivered

Once a message has reached someone's device, an edit or delete is a request to their software, not a guarantee.

Edit

A new message that references the original and carries replacement content. Clients show the latest, maybe with an "edited" marker and history.

Delete for everyone

A message asking recipients to hide the original. receipts/1.0's deleted state is the other direction: the recipient reporting that they deleted it.

Worth being explicit: authcrypt messages are repudiable, so an edit doesn't create evidence either way.

formatting

Bold, italics, underline, code, links

ApproachUpsideDownside
Markdown in contentReadable even unrendered; easy to typeMany dialects; no underline in most; ambiguous edge cases
A formatted field beside plain contentOld clients keep working; formatting is explicitTwo versions of the text can disagree
Style ranges over plain textNo markup to parse or sanitizeOffsets break if text is edited; awkward to author

Matrix takes the second route: a plain body plus an optional formatted_body in a restricted HTML subset.

rendering is an attack surface

Encrypted doesn't mean safe to display

  • Never render sender-supplied HTML directly. Use an allow-list of elements, or a format that can't express scripts at all.
  • Show where a link really goes. Formatted text can say one URL and point to another.
  • Treat embedded media as untrusted input to image and video decoders.

links, previews and embeds

Who fetches the preview?

The recipient fetches it

Every recipient's device contacts the linked site, revealing their IP address and when they read the message.

The sender attaches it

The sender's device builds the preview (title, image) and sends it as an attachment. Recipients contact nothing. The sender can lie, but they could lie in the text anyway.

Larger embeds (photos, video) fit the encrypt-upload-share pattern of media-sharing/1.0. See "Sharing and Storing Files".

not everyone will support it

Degrade gracefully

  • Always include plain content that makes sense alone, e.g. a quoted line before a reply's text.
  • Ask what the other side supports with Discover Features 2.0 before sending reactions or edits it would ignore.
  • Several small protocols (reactions, edits, formatting), not one big one, so agents can adopt them one at a time.
  • In groups, members will have different support. Plan for mixed groups from the start.

a sketch

A reply with formatting, readable by a basic client

{
  "type": "https://didcomm.org/basicmessage/2.0/message",
  "lang": "en",
  "body": {
    "content": "> Lunch at 12?\nYes, see you *there*",
    "reply_to": "msg-8812",          // hypothetical
    "formatted": {                    // hypothetical
      "format": "markdown",
      "text": "Yes, see you *there*"
    }
  }
}
  • A basic client shows content and ignores fields it doesn't know.
  • A richer client uses reply_to to link to the quoted message, and renders formatted.
  • Whether extending basicmessage like this is acceptable, or a new message type is needed, is itself a question for the group.
