the key property

A DIDComm message is a self-contained file.

Security lives in the envelope, not the connection. So the message can travel any way at all, and still be verified and decrypted at the other end.

The filesystem transport

Since files can be moved over AirDrop or AWS Snowball, attached to a chat, carried on USB thumb drives, or managed by WebDAV, a file-oriented transport enables flexible communications patterns … This includes a "sneakernet" that is full-featured even when its offline and highly asynchronous.DIDComm Filesystem Transport Extension
  • Endpoint: a file: URI (or anything folder-like: S3, a git repo) that the sender can write and the recipient can read.
  • Ordering: by modification time, or explicit prefixes like 01--msg.dcem.
  • Busy folders can nest per thread: <thid>.thid/.

another existing extension

Email: already everywhere in logistics

The email transport extension uses a mailto: endpoint. DIDComm messages ride as attachments; the body stays for humans.

  • Works with the email systems partners already run, with no new infrastructure.
  • Agents must process DIDComm-typed attachments, and may sniff for *.dcem files a person attached by hand.
  • Email headers are hints only; the DIDComm content is authoritative.

evidence

Authcrypt is deliberately deniable

The default envelope proves the sender only to the recipient, who can't prove it to anyone else. For a dispute, that's not enough.

DIDComm Encrypted messages are repudiable. If non-repudiation is required for a particular protocol message, the message MUST be signed before encryption.Message Signing — Uses of Signatures

So shipping notices, receipts and inspection results would use anoncrypt(sign(plaintext)): confidential in transit, provable afterwards.

documents

Attachments by value or by reference

  • base64 or json: the document travels inside the message. Best offline.
  • links + hash: the document stays elsewhere; the hash is required so the receiver can check what it fetched.
  • jws: an attachment can carry its own signature, and the signer need not be the message's author (say, a lab certificate forwarded by a carrier).
  • byte_count: lets the receiver decide whether to fetch it now.
{
  "id": "coa-1",
  "filename": "certificate.pdf",
  "media_type": "application/pdf",
  "byte_count": 184233,
  "data": {
    "links": ["https://…/certificate.pdf"],
    "hash": "<multihash>",
    "jws": { … }
  }
}

many parties, one shipment

Threads that span organisations

Parent threads

A shipment is one thread; customs clearance or a payment is a child thread linked with pthid. With more than two parties, each must learn the parent from the first child message it sees, so repeat pthid on every message.

Ordering across hops

Messages that arrive by USB stick, email and HTTPS won't arrive in order. The Advanced Sequencing headers detect gaps without assuming a single transport.

a sketch

One container, four transports

Manufacturer

Signs and encrypts a shipping notice for the carrier; sends over HTTPS.

Ship

No connectivity. Inspection messages pile up in an outbox folder on the vessel.

Port

The folder is copied off by USB or synced on arrival; queued messages deliver in order.

Customs

Receives a signed manifest by email; verifies the signatures back to the manufacturer.

Buyer

Holds the full signed chain of messages as evidence.

shared folders

One folder, many readers

The filesystem extension explicitly allows duplex and fan-out: a shared endpoint folder can serve a group, or a public broadcast.

  • Encryption still decides who can read what; the outer envelope shows who each message is for.
  • Writers create msg.dcem.tmp and rename it, so readers never see half-written files.
  • Readers clean up messages addressed only to them once processed.

the long tail

Evidence has to outlive the keys

A signed manifest may need to be checked years later, after the signer has rotated keys, changed DIDs, or gone out of business.

  • Verifying needs the DID document as it was when the message was signed.
  • Some DID methods keep history; did:peer doesn't, so the parties must archive what they saw.
  • Algorithms age too. (See "DIDComm and Post-Quantum Cryptography".)
