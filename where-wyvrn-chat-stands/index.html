wyvrn-chat — positioning notes

Where wyvrn‑chat
Stands

Strengths, weaknesses, and a plain look at what the rest of the DIDComm ecosystem has — and hasn't — already solved.

a peer-to-peer DIDComm v2 chat app · wyvrn-cloud

what it is

A chat app.
Not a wallet with messaging bolted on.

Contacts on the left, messages on the right — basicmessage/2.0, real read receipts, group chats, profiles. DIDComm v2 as the transport, not as a means to issue a credential.

No central server

Identity, storage, and delivery all live at the edges — a mediator relays, it never holds a copy of the conversation.

Native + web

One Rust core. Browser (wasm), desktop, and Android from the same codebase — see the other deck for how.

Encrypted at rest

PIN or passkey-gated vault key; SQLCipher on native. Never regenerates an existing identity.

the gap

Most of the DIDComm ecosystem builds
credential wallets, not chat apps.

Bifold — the OpenWallet Foundation's own reference wallet, built on Credo — lists peer-to-peer messaging as a capability. A real chat UI is on its roadmap, not shipped.

We didn't find a consumer DIDComm chat app comparable to wyvrn-chat anywhere in the Aries/Credo ecosystem. Most DIDComm traffic today issues and presents credentials — it doesn't carry a conversation.

positioning3 / 15
strength — multi-device identity

One identity, several devices,
independent keys. Nobody else ships this.

ACA-Py

Explicitly one public DID per wallet. Its own "multi-device" story is multi-tenant — separate wallets on one server, not one identity across a person's own devices.

Veramo

Its "multi-device" pattern splits one agent into backend microservices — key custody, data, frontend. Orthogonal to a person actually holding two phones.

wyvrn-chat's multi-device/1.0: an Identity DID with one keyAgreement per device, a Device DID per device for coordination, no private key ever leaves the device that generated it.

positioning — see also: Identity DID, Device DID4 / 15
strength — didcomm/v2+cbor

The spec has debated this since 2021.
We shipped it.

DIDComm Messaging v2.1 names +cbor/+msgpack/+protobuf as future possibilities. A real 2021 spec-repo issue — "Should we flip to CBOR?" — argued JSON creates real overhead. It was never resolved.

What it actually is

The same JWE general-form structure. iv/ciphertext/tag/encrypted_key as real CBOR byte strings instead of base64url text.

What it buys

No ~33% base64 blowup on top of the ciphertext and every other binary field. Negotiated per-recipient, off their advertised accept.

decentralized-identity/didcomm-messaging issue #207 (2021) — no shipped Aries/Credo/DIDComm-rs/Veramo implementation of a CBOR envelope was found.

positioning5 / 15
strength — the mediator itself

One mediator. Both eras.
Built to run more than one copy.

v1 and v2/v3/v4

The full legacy AIP1/AIP2 envelope family, same service, same storage — not a separate deployment.

SQLite, MySQL, or Postgres

One SQL schema across three backends — not a single-instance demo store.

Horizontally scalable

Live delivery decoupled through a WS↔HTTP relay; any replica can deliver to a DID connected on a different one.

positioning6 / 15
strength — combined, not isolated

Credo's mediator can push. It has nothing to combine that with.

didcomm-mediator-credo implements Aries RFC 0734 — real, functional, FCM only, no APNs mentioned anywhere in its own repo. wyvrn adopted the exact same protocol.

The difference isn't the push protocol. It's that any of a person's enrolled devices — not just the one that happened to register — can be woken, because multi-device/1.0 already knows about all of them.

github.com/openwallet-foundation/didcomm-mediator-credo — ~98 commits, 18 stars, 37 forks: real and functional, not a widely-deployed production mediator.

positioning8 / 15
weakness — key storage

Software-derived, not hardware-backed.

The vault key comes from a PIN (PBKDF2) or a passkey's prf output. SQLCipher protects the file at rest. Real, but it's not the same guarantee as a hardware secure element.

Aries' own storage layer, Askar, already does encrypted-at-rest SQLite/Postgres — parity with wyvrn, not an advantage either way. But Askar-based wallets have a path to Android StrongBox / iOS Secure Enclave. wyvrn-chat doesn't use either yet.

github.com/openwallet-foundation/askar; OWASP MASTG on hardware-backed key storage.

positioning9 / 15
weakness — the same cbor, cuts both ways

Only two wyvrn endpoints ever see the saving.

Every real Aries, Credo, or other DIDComm peer today only understands +json. didcomm/v2+cbor negotiates down to plain JSON automatically when the other side doesn't advertise it —

— which means, in practice, almost every message wyvrn-chat sends to the wider ecosystem today gets none of the benefit slide 5 described.

positioning10 / 15
weakness — the accepted cost, revisited

Every roster change is a broadcast.

Enroll a device, revoke one, promote, demote — each mints a new Identity DID and rotates every contact onto it. A person who churns devices often means real, recurring chatter no single-key architecture pays.

positioning — see also: multi-device/1.0, Motivation11 / 15
weakness — a young project vs. a mature one

ACA-Py

Years of production credential-network deployments, a large community, plugins, third-party tooling. Battle-tested at a scale wyvrn-chat hasn't approached.

wyvrn-chat

A single-team project. No iOS build exists yet — needs a real Mac. group-chat/1.0 is still "Proposed," not hardened by outside use.

positioning12 / 15
weakness — the mediator isn't fully open

ACA-Py and Credo-TS: Apache 2.0, no gate.
wyvrn-mediator: a real license check at startup.

Not a technical limitation — a plain business-model difference worth naming rather than glossing over. Anyone standing up their own mediator instance needs a valid wyvrn-license first.

positioning13 / 15
where this leaves us

Two real gaps closed. Two real costs still open.

Closed

A real chat app on DIDComm, not a wallet. Multi-device identity with no shared key — something we could not find shipped anywhere else in the ecosystem.

Still open

Hardware-backed key storage. Real-world benefit from the CBOR profile, which today helps almost nothing it talks to.

Neither list is closed. This is a snapshot, not a verdict.
