the spec's own history

CBOR was discussed, and deferred.

At multiple points in the creation of this spec the community discussed switching to CBOR as a primary encoding format to replace JSON. Two reasons prevented that switch: The maturity of the JSON related standards as compared to CBOR related standards, and the cost of switching so late in spec development.DIDComm Messaging v2.1 — Future Work, Additional Encodings
Future encodings might introduce binary serializations. Each innovation like this MUST specify a deterministic and reliable method for indicating the alternative encoding used.same section

where the bytes go

Base64 inside JSON, inside base64

A DIDComm encrypted message is a JWE in General JSON format: ciphertext, IV, tag and protected header are all base64url strings, each about 4/3 the size of the bytes they carry.

Encrypt only

Ciphertext is base64url'd once: roughly 1.33× the plaintext, plus headers.

Sign, then encrypt

The JWS payload is base64url'd, then the whole JWS is encrypted and base64url'd again: roughly 1.8×.

Binary attachments

Images and files ride as base64url too, before any of the above.

Plus JSON key names like "protected" and "recipients" repeated in every message. CBOR carries raw bytes and can use small integer keys.

4/3 per base64url layer is exact up to padding; two nested layers give 16/9 ≈ 1.78. Worth measuring real messages before presenting, including per-recipient header overhead.

the hard part

Authcrypt doesn't map across directly

DIDComm's default envelope, authcrypt, uses ECDH-1PU, which mixes the sender's static key into key agreement so the recipient knows who sent it. It's an individual IETF draft that expired in 2021, and it's in neither the JOSE nor the COSE registry.

What COSE has

ECDH-ES (ephemeral–static), which matches anoncrypt, and ECDH-SS (static–static). Neither is ECDH-1PU. The COSE-HPKE draft uses HPKE's base and PSK modes only, not the sender-authenticated mode RFC 9180 defines.

So a CBOR profile must…

…define or register an ECDH-1PU equivalent for COSE, or change how sender authentication works in that profile.

signalling it

The spec already sketched the media type

If future versions of this spec allow binary encodings, variations like application/didcomm-encrypted+cbor … may become reasonable.Message Formats — DIDComm Encrypted Messages

A receiver lists what it accepts, in preference order, in its service endpoint. A sender that can't produce CBOR just uses the next entry.

"serviceEndpoint": {
  "uri": "https://example.com/didcomm",
  "accept": [
    "didcomm/v2;enc=cbor", // hypothetical
    "didcomm/v2"
  ]
}

routes complicate it

Every hop has to agree

Declaring a profile is a promise about every publicly visible hop of the inbound route, not only the final endpoint. A CBOR recipient behind a JSON-only mediator can't advertise CBOR end to end.

  • Mixed routes: could the outer forward layers stay JSON while the innermost envelope is CBOR?
  • A forward attachment can carry any bytes, so in principle yes. But the attachment's media type would need to say so.

a CBOR profile would need to pin down
  • Integer labels for plaintext headers (id, type, thid, body…), or keep text keys.
  • How body is encoded: native CBOR, or JSON inside.
  • Attachments: raw bytes instead of base64; what happens to json attachments.
  • The authcrypt question from earlier.
  • from_prior as a CWT instead of a JWT.
  • Out-of-band invitations in QR codes, where size matters most.

the costs

Why it might not be worth it

Two of everything

Implementations and mediators that support both encodings carry two code paths and two sets of test vectors.

Harder to debug

You can't read a CBOR message in a log without a decoder.

Interop first

A binary profile only pays off once the other side supports it. Until then, everyone sends JSON anyway.

Compression exists

Ciphertext doesn't compress, but for many links, HTTP compression of the JSON framing may be enough.

when it pays off

Constrained links, not web servers

Bluetooth

Small writes; every byte saved is fewer chunks. (See "DIDComm over Bluetooth".)

Small devices

Less parsing, less memory, smaller messages. (See "DIDComm on Small Devices".)

QR codes

Out-of-band invitations are size-limited by what a camera can read.

an experiment

Worth measuring before deciding

An experimental CBOR profile has been tried in wyvrn. So far it helps almost nothing it talks to, because almost nothing on the other end speaks it. Interop, not encoding, is the real hurdle.

A different route in the registry: mesh/1.0 doesn't CBOR-encode the standard envelope at all. It defines its own binary packet format and a compact session-key envelope for BLE and LoRa, with JSON kept for debugging and the internet.

Useful next step for the group: agree on a few reference messages and measure JSON vs. CBOR sizes for each.
