The case for CBOR · the spec's own history

CBOR was discussed, and deferred.

At multiple points in the creation of this spec the community discussed switching to CBOR as a primary encoding format to replace JSON. Two reasons prevented that switch: The maturity of the JSON related standards as compared to CBOR related standards, and the cost of switching so late in spec development.DIDComm Messaging v2.1 — Future Work, Additional Encodings

The case for CBOR · where the bytes go

Base64 inside JSON, inside base64

A DIDComm encrypted message is a JWE in General JSON format: ciphertext, IV, tag and protected header are all base64url strings, each about 4/3 the size of the bytes they carry.

Encrypt only

Ciphertext is base64url'd once: roughly 1.33× the plaintext, plus headers.

Sign, then encrypt

The JWS payload is base64url'd, then the whole JWS is encrypted and base64url'd again: roughly 1.8×.

Binary attachments

Images and files ride as base64url too, before any of the above.

Plus JSON key names like "protected" and "recipients" repeated in every message. CBOR carries raw bytes and can use small integer keys.

didcomm in cbor3 / 26
4/3 per base64url layer is exact up to padding; two nested layers give 16/9 ≈ 1.78. The "What it measures" section has real numbers: signed + anoncrypt is where JSON pays the double layer, and CBOR saves 48–58% there.

The hard parts · authcrypt

Authcrypt doesn't map across directly

DIDComm's default envelope, authcrypt, uses ECDH-1PU, which mixes the sender's static key into key agreement so the recipient knows who sent it. It's an individual IETF draft that expired in 2021, and it's in neither the JOSE nor the COSE registry.

What COSE has

ECDH-ES (ephemeral–static), which matches anoncrypt, and ECDH-SS. Neither is ECDH-1PU. COSE-HPKE uses HPKE's base and PSK modes only.

So a CBOR profile must…

…define an ECDH-1PU equivalent for COSE, or change how sender authentication works in that profile.

One way to do it

Keep ECDH-1PU and give it a text COSE alg label, which RFC 9052 allows. Derive keys with COSE's HKDF context and bind the content tag into it, as JOSE does. The wyvrn experiment does this.

The hard parts · signalling it

A profile name, and the first byte

An open proposal, didcomm-messaging#463, names a profile, didcomm/v2+cbor, and media types like application/didcomm-encrypted+cbor, which the spec had already sketched.

A receiver lists what it accepts in its service endpoint. A sender that can't produce CBOR uses didcomm/v2.

The deterministic indicator

A JSON message starts with { (0x7B). A CBOR one starts with a byte from 0x80 to 0xFF: a map, an array, or a COSE tag. The bytes say which encoding they are.

"serviceEndpoint": {
  "uri": "https://example.com/didcomm",
  "accept": [
    "didcomm/v2",
    "didcomm/v2+cbor"
  ]
}
didcomm in cbor7 / 26
PR #463 ("WIP: CBOR encoding", opened August 2025) is still open. Its "Encoding Detection" section gives the first-byte rule, which meets the spec's own requirement for "a deterministic and reliable method for indicating the alternative encoding". A COSE_Encrypt is CBOR tag 96 (bytes d8 60); a COSE_Sign1 is tag 18 (d2).
The hard parts · routes complicate it

Every hop has to agree, or negotiate

Declaring a profile is a promise about every publicly visible hop of the inbound route. A CBOR recipient behind a JSON-only mediator can't advertise CBOR end to end.

  • Negotiating per hop works: the inner message follows the recipient's accept, each forward follows its mediator's. A routing key with no endpoint to ask (a did:key) follows the recipient's.
  • The packed inner message rides as an attachment: raw data.binary in a CBOR forward, the standard data.base64 in a JSON one, data.json if it's JSON.
  • Mixed routes cost bytes: a CBOR message inside a JSON forward is base64'd twice. See the numbers.
didcomm in cbor8 / 26
Spec: Negotiating Compatibility — "When Alice declares that she accepts didcomm/v2, she is making a declaration about more than her own endpoint..." data.binary is not in #463; the PR only says the attachment's media_type becomes application/didcomm-encrypted+cbor. A did:key routing key has no service, so it can't advertise anything; falling back to JSON there would break the recipient's route-wide promise.

What it measures · method

Packed for real, not estimated

Every number is the byte length of a message produced by the actual pack, forward and pickup code, with real keys and real did:peer:4 DIDs. Median of five runs.

Three payloads

A short chat message ("Hello world!"), 1 KiB of text, and a 10 KiB binary attachment (random bytes, like a compressed photo) carried as data.base64 in JSON and raw data.binary in CBOR.

Two DID styles

Long form did:peer:4 carries the whole DID document inline (806 characters here). Short form is just the hash (57 characters).

Every hop

Direct messages, the forward to a mediator for each mix of mediator and recipient encodings, and the delivery the recipient picks up.

Envelopes: XC20P anoncrypt, A256CBC-HS512 authcrypt, EdDSA signatures, X25519 keys. Reproduce with cargo run -p didcomm-quickstart --example message_sizes.

Authcrypt carries the sender's kid as apu. The JSON form also repeats it as skid, inside a base64url'd protected header. The COSE form omits skid, which the spec allows: DIDComm Messaging v2.1, Security → Message Encryption → "ECDH-1PU key wrapping and common protected headers", last paragraph: "authcrypt implementations MUST be able to resolve the sender kid from the apu header if skid is not set" (the 1PU draft, §2.2.1, doesn't require skid). The same section requires apu to contain the skid value, so nothing is lost. With long-form DIDs that saves 816 bytes (4,510 → 3,694).

What it measures · what's left

After CBOR, the bytes are identifiers

DIDs

Kids, apu, from/to, next: all text in both encodings. A long-form all-CBOR forward is still 6,627 bytes; short form, 1,388.

Repeated headers

COSE repeats the shared key-agreement headers in every recipient. Dropping the duplicate skid (it repeats apu) saved 816 bytes per long-form authcrypt message.

Attachments

Raw data.binary in CBOR: a 10 KiB photo costs 10 KiB, not 13.3. What's left is the photo itself.

A final note about skid header: since the 1PU draft does not require this header, authcrypt implementations MUST be able to resolve the sender kid from the apu header if skid is not set.DIDComm Messaging v2.1 — ECDH-1PU key wrapping and common protected headers
didcomm in cbor20 / 26
Spec location for skid: v2.1, Security → Message Encryption → "ECDH-1PU key wrapping and common protected headers", final paragraph. #463's COSE authcrypt header list (ephemeral key, party u identity, party v identity, algorithm) has no skid either. Caveat: "Message Layer Addressing Consistency" says the plaintext from MUST match skid; with skid absent that means the sender kid taken from apu, which is what wyvrn checks. JWE puts the shared epk/apu/apv once in its protected header; COSE's per-recipient layering repeats them for each recipient (each device of a multi-device DID).

Is it worth it? · the costs

Why it might not be worth it

Two of everything

Implementations and mediators that support both encodings carry two code paths and two sets of test vectors.

Harder to debug

You can't read a CBOR message in a log without a decoder.

Interop first

A binary profile only pays off once the other side supports it. Until then, everyone sends JSON anyway.

Compression exists

gzip recovers part of the base64 tax, but not all of it: measured, gzipped JSON is still bigger than plain CBOR almost everywhere.

Is it worth it? · when it pays off

Constrained links, not web servers

Bluetooth

Small writes; every byte saved is fewer chunks. (See "DIDComm over Bluetooth".)

Small devices

Less parsing, less memory, smaller messages. (See "DIDComm on Small Devices".)

QR codes

Out-of-band invitations are size-limited by what a camera can read.

Is it worth it? · an experiment

Half the bytes, if both ends speak it

wyvrn's experimental profile now follows #463: COSE envelopes, CBOR plaintext. Mediated end to end, a typical chat message's forward is 46% smaller, and the pickup delivery 48% smaller. Almost nothing on the other end speaks it yet, so interop, not encoding, is still the real hurdle.

A different route in the registry: mesh/1.0 doesn't CBOR-encode the standard envelope at all. It defines its own binary packet format and a compact session-key envelope for BLE and LoRa, with JSON kept for debugging and the internet.

Next step for the group: shared reference messages and test vectors for each encoding, so other implementations can check their sizes and their bytes.

Open questions

  • Is #463 worth finishing now, or only once someone needs it?
  • How should authcrypt work in COSE: text labels for ECDH-1PU, or a registration?
  • Should #463 define data.binary for raw attachment bytes, with media_type saying what they are?
  • Long-form DIDs cost more bytes than the choice of encoding. Should they ever be on the wire?
