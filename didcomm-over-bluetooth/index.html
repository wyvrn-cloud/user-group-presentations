the scenario

Two phones, one room, no internet.

Today, a message between them goes up to a mediator on the internet and back down, even though the phones are a metre apart. With no connection at all (a field site, a basement, a plane), nothing moves.

Latency

A round trip to a server for a message to the next desk.

Availability

No internet means no delivery, even when the recipient is right there.

Metadata

The mediator learns about traffic that never needed to leave the room.

the spec already says

Bluetooth is named in DIDComm's own requirements

Transport-agnostic (usable over HTTPS 1.x and 2.0, WebSockets, BlueTooth, chat, push notifications, libp2p, AMQP, SMTP, NFC, sneakernet, snail mail; supports both simplex and duplex; works offline; doesn't assume client-server or synchronous or real-time; allows paired or n-wise or public broadcast usage)DIDComm Messaging v2.1 — Requirements

And security doesn't depend on the link: the encryption envelope "provides trust as a feature of each message". A Bluetooth link needn't be trusted at all.

bluetooth realities

Encrypted DIDComm messages are big for Bluetooth

BLE GATT

Available everywhere, but each write is small: the default ATT MTU is 23 bytes, negotiable up to about 512. Messages must be chunked and reassembled.

BLE L2CAP channels

Connection-oriented channels give a proper byte stream with flow control. Better for bulk; platform support varies.

Classic (RFCOMM)

A serial stream with more throughput, but patchy on phones, especially iOS.

A receiver can publish max_receive_bytes so senders know when to fall back to the mediator for large messages.

the hardest part

Finding each other without being trackable

A DID document is fairly static; "who is nearby" changes by the minute. To connect, a device has to advertise something. If that's a stable identifier, anyone with a scanner can follow it around.

Known contacts

Advertise short-lived identifiers derived from a secret the two parties already share, so only contacts recognise each other, and the value changes every few minutes.

First contact

Use an out-of-band invitation, for example a QR code, to exchange DIDs, then switch to Bluetooth for the conversation.

didcomm over bluetooth6 / 12
Rotating identifiers derived from a shared secret is the same idea used by several proximity systems. The spec's out-of-band section also warns that identifiers passed in a QR code are no longer private and should be rotated over a secure connection if privacy matters.
two-way links

A Bluetooth link is naturally two-way

DIDComm transports are one-way by default. The return-route extension already covers "send replies back over the connection I opened": return_route: all or thread.

It's defined for the directly connected pair only, not through routing keys, which is exactly the Bluetooth case.

Choosing a path, per message

Is the peer nearby?

Recently seen advertising, and a link can be opened.

Does it fit?

Under the peer's max_receive_bytes and worth sending locally.

Try Bluetooth

Send and wait for a transport-level acknowledgement.

Fall back

No ack in time? Send the same message through the mediator, as the failover rule says.

the consequence

Some messages will arrive twice

A local send that succeeded but whose ack was lost gets retried through the mediator. The receiver later picks up a copy it already has.

  • Message ids are unique across all interactions the parties can see, which makes them good dedup keys.
  • Keep a window of recently seen ids; drop repeats.
  • For ordering-sensitive protocols, the Advanced Sequencing headers detect gaps and reordering across the two paths.

a possible extension

What a Bluetooth transport extension could specify

EndpointA URI or object meaning "reachable locally", with no stable identifier in it
DiscoveryRotating advertisement identifiers for known contacts; out-of-band for first contact
FramingLength-prefixed messages; chunking rules for GATT; L2CAP where available
Media typeCarried in the frame header, like HTTP's Content-Type
DuplexReuse the existing return_route header
DeliveryA transport ack, so senders know when to fall back
