the assumption

DIDComm's tooling quietly assumes
one identity, one keypair.

Generate a DID, hold its keyAgreement secret, unpack with it. Almost every quickstart, every tutorial, every sample resolver in the ecosystem is built around exactly one device holding exactly one private key per identity.

the problem

Real people aren't one device.

📱 Phone

Where most messages actually arrive. Not always on, not always the one someone picks up first.

💻 Laptop

Where they'd rather type a long reply. Should see everything the phone sees.

💻 Tablet

Added later, by someone who already has an identity and doesn't want a second one.

A contact should reach one identity — not have to know which of three devices happens to be reachable right now.

the naive fix

Copy the same keypair
to every device.

Simple. Ships fast. It's the first thing most of us reach for — until the cost becomes obvious:

One compromised device exposes every message ever sent to the identity — for as long as the compromise goes unnoticed.

checked, not assumed

Per-device keys aren't blocked by DIDComm.
The spec text already points that way.

"A sender only uses the first keyAgreement entry it finds" — a claim about how one single-recipient-oriented resolver happens to behave, not something the spec requires.

DIDComm Messaging v2.1's own recommended default is the opposite: encrypt to every keyAgreement entry a recipient's document lists, so that recipient "can decrypt his messages on any device he controls, without sharing keys across his devices."

the split

One way to split it: two kinds of DID, not one.

content-facing

Identity DID

One keyAgreement entry per enrolled device. One authentication entry per trusted device only. This is what contacts encrypt to and address — forever, across every rotation.

device-to-device only

Device DID × N

One per device, independently generated, never shared with a contact. Exists so an unenrolled device — no Identity DID key yet — has somewhere to receive its own enrollment reply.

identity did · device did — the approach6 / 15
roles

Two roles. One boolean: has an authentication key.

device

Holds its own keyAgreement key — can send and receive as the identity immediately. Cannot enroll, revoke, or change trust; it has nothing to sign a rotation with.

trusted device

Also holds an authentication key. Can single-handedly enroll, revoke, promote, or demote — every one of those is the same operation underneath (more on that shortly).

The founding device starts trusted. A newly enrolled device starts untrusted, always — promotion is a separate, explicit step, never automatic.

enrollment, step by step

Laptop prepares

Generates its own Device DID + its own keyAgreement keypair, offline. Never receives anyone else's private key.

QR scan

Real out-of-band/2.0 invitation from the phone's Device DID. No key material in it — just a route.

enroll-request

Laptop sends its new public key over that route. Physical possession of the QR is the whole trust basis — same as Signal, WhatsApp.

enroll-response

Phone mints a new Identity DID document, signs from_prior, replies with the full roster.

Fan-out

Phone rotates every other sibling and every contact onto the new DID. Both devices now independently receive as the identity.

on the wire — a sketch

What the two messages could carry

  "body": {
    "device_id": "laptop",
    "device_did": "did:peer:4...laptop",
    "key_agreement_public": "z6LSb..."
  }
}
{
  "type": ".../device-enroll-response",
  "body": {
    "identity_did": "did:peer:4...v2",
    "from_prior": "eyJhbGci...",
    "roster": [ … ],
    "rotates": false,
    "rotation_seq": 1
  }
}

No field in either message is ever a private key. rotation_seq exists purely so an out-of-order fan-out can't resurrect a state a newer rotation already superseded.

the cost of this approach

did:peer's value is a hash of its own document.

Enroll a device. Revoke one. Promote, demote — any of those changes the document, which changes the Identity DID's own value. Every roster change means a from_prior rotation broadcast to every contact.

That's the trade-off: more rotation traffic, in exchange for never sharing a private key between devices.

identity did · device did — trade-offs11 / 15
key rotation

One mechanism. Four use cases.

Enroll

New keyAgreement entry added to a fresh document.

Revoke

Departing device's entries dropped — cut off the instant the new document ships.

Promote

Device supplies its own authentication public key; a trusted sibling adds it.

Demote

Any trusted device can drop another's authentication entry, unilaterally.

Every case: mint a new document, sign from_prior with an authentication key the old document already lists, fan it out. No private key ever moves between devices, in any of the four.

identity did · device did — rotation12 / 15
security properties — and an open problem

What holds

  • A revoked device is cut off from both content and rotation authority the instant the new document publishes.

  • A compromised untrusted device can read content — but can never forge a rotation. It has no authentication key to sign with.

What doesn't

Lose your last trusted device and this approach, on its own, has no recovery — nothing left that can sign a rotation. The simplest mitigation is UX: promote a second device early.

recap

The approach, in three numbers.

2

DIDs per identity — Identity + one Device DID per device

1

rotation mechanism covering enroll / revoke / promote / demote

0

private keys ever transmitted between devices

No new cryptography. Just existing DIDComm pieces put together: multiple keyAgreement entries, out-of-band/2.0 for pairing, and from_prior for rotation.
